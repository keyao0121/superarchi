# Pascal Editor · Dopame 版项目说明

本文说明 `acde` 分支在上游 Pascal Editor 之上做了什么：把编辑器移植到 Dopame（acde 运行时），并在其中内置一个 AI 设计团队。分三部分：

1. [项目说明](#一项目说明)：这是什么、怎么构建和使用、代码在哪。
2. [移植说明](#二移植说明)：acde 运行时缺什么、每一项怎么解决的、踩过的坑。
3. [自进化设计](#三自进化设计未实现)：AI 团队怎样从工作里学习。**只有设计，尚无代码。**

---

## 一、项目说明

### 1.1 这是什么

Pascal Editor 是一个开源的 3D 建筑编辑器（墙、房间、门窗、家具，2D 平面图与 3D 视图同步）。上游面向浏览器。本分支让它作为一个 **acde 应用**安装进 Dopame 桌面，并加上两种让 AI 操作场景的方式：

| 方式 | 谁是 AI | 入口 |
|---|---|---|
| 内置 AI 团队 | 应用自己调用的大模型 | 编辑器右侧的「AI 团队」面板 |
| 外部 agent | 同一台机器或经 SSH 连过来的 MCP 客户端（Claude Code、Codex 等） | `bun run acde:mcp` |

两种方式用的是同一套场景工具（仓库自带的 Pascal MCP server），改动都落到同一个项目库，打开着的编辑器实时跟随。

### 1.2 内置 AI 团队

对「总管」说一句话，例如「把房间扩到 30 平米，布置成双床房」：

1. **总管**读一份场景摘要，把这句话拆成有顺序的任务，写到工作表上。总管自己不改场景。
2. **员工**按顺序逐个执行，每人只拿本职的一小组工具：

   | 员工 | 做什么 | 能否改场景 |
   |---|---|---|
   | 平面员工 | 房间、墙、门、窗 | 能 |
   | 室内员工 | 家具、设备、饰面 | 能 |
   | 校核员工 | 核对面积、门、碰撞、朝向；不合格就打回 | 只读 |
   | 出图员工 | 报面积表 | 只读 |

3. 每一步改动实时出现在 2D/3D 里，并在**修改单**里留一行说明。
4. 校核不通过时，发现的问题会变成返工任务派回给对应员工，再复查一次（最多一轮）。
5. 全部做完后等人**验收**；也可以**撤回**，场景回到这句话之前的样子。

面板自上而下是：总管对话、工作表（待办 / 进行中 / 待验收 / 完成）、修改单和面积表。面板只在 acde 里显示，普通网页版不受影响。

**模型设置**：面板右上角的设置按钮里填接口地址、模型名和 API key。任何 OpenAI 兼容的对话接口都可以（需要支持函数调用）。key 存在应用私有数据目录的 `agent-model.json` 里，文件权限 600，不进代码库，页面读不回来。

**已知边界**：

- 员工是顺序执行，不是并行。
- AI 看不到画面，只靠工具读结构和尺寸。
- 不出效果图、PDF、CAD；出图员工只报面积表。
- 对话和工作表只存在后端进程里，关掉应用就清空。
- 同一时刻只能有一个项目在跑 AI 任务。

### 1.3 外部 agent 经 MCP 接入

```bash
bun run build                                  # 仓库根目录，只需一次
bun apps/editor/scripts/acde/mcp.ts            # stdio 方式的 MCP server
```

这个入口会自动指向已安装的 acde 应用的项目库。MCP 客户端在本机直接运行这条命令；在另一台机器上则把同一条命令放在 `ssh <用户>@<主机>` 后面。agent 先 `load_scene` 加载编辑器里正打开的项目，之后的修改才会实时显示。

### 1.4 构建、安装、测试

在 `apps/editor` 下，一律用包装好的脚本，不要裸跑 `acde …`：

| 命令 | 作用 |
|---|---|
| `bun run acde:prepare` | 准备 acde 构建需要的本地资源（见 2.3） |
| `bun run acde:dev` | 开发模式运行 |
| `bun run acde:build` | 构建 acde 包 |
| `bun run acde:install` | 构建并安装到本机的 acde / Dopame |
| `bun run acde:test` | 在 acde 里跑端到端测试（单 worker、英文环境） |
| `bun run acde:mcp` | 见 1.3 |

安装后正在运行的应用仍是旧后端，需要关掉重开。

单元测试是 `bun run test`（`apps/editor`）和各包自己的 `bun test`。仓库根目录另有 `bun run check:acde-compat`，在 CI 里拦截新引入的 acde 不支持的 Web API。

### 1.5 代码在哪

| 位置 | 内容 |
|---|---|
| `apps/editor/acde.config.jsonc` | acde 应用配置 |
| `apps/editor/lib/acde/` | acde 下的后端环境、语言、页面配置、MCP 数据目录 |
| `apps/editor/scripts/acde/` | 资源准备步骤、MCP 入口、场景主机打包 |
| `apps/editor/lib/agent/` | AI 团队后端 |
| `apps/editor/components/agent-panel.tsx` | AI 团队面板 |
| `apps/editor/app/api/agent/settings/` | 模型设置接口 |
| `apps/editor/app/api/scenes/[id]/agent/` | AI 团队的状态流（SSE）和动作接口 |
| `apps/editor/e2e/` | acde 端到端测试 |
| `packages/core/src/platform/acde.ts` | `isAcde()` 检测 |
| `scripts/check-acde-compat.ts` | 不支持的 Web API 检查 |

AI 团队后端各文件的分工：

| 文件 | 职责 |
|---|---|
| `employees.ts` | 员工的角色提示词、各自的工具清单、总管的拆任务提示词 |
| `scene-agent.ts` | 一次任务的编排：拆任务、员工循环、返工、验收、撤回 |
| `scene-host.ts` | 进程内的 Pascal MCP server（单独打包，见 2.4） |
| `model.ts` | OpenAI 兼容接口的调用 |
| `session.ts` | 每个项目一份的会话状态和订阅 |
| `settings.ts` | 模型设置的读写 |
| `digest.ts` | 场景摘要（楼层、房间面积、数量） |

### 1.6 一次任务的数据流

```text
面板 ──POST 一句话──▶ 后端 /api/scenes/:id/agent
                         │
                         ├─ 总管：模型调用一次 ─▶ 任务列表
                         │
                         ├─ 每个员工：模型 ⇄ 场景工具（循环，至多 30 步）
                         │         │
                         │         └─ 进程内 MCP server ─▶ 写项目库 + 记一条场景事件
                         │
                         └─ 状态每变一次，整份推给面板（SSE）

编辑器页面 ◀──场景事件（SSE）── 项目库        ← 3D/2D 实时更新走的是这条，和外部 agent 相同
```

## 二、移植说明

### 2.1 策略

所有改动尽量只在「检测到 acde」或「检测到缺少某个能力」时生效，普通浏览器下行为不变，方便继续跟上游合并。能用能力检测的地方用能力检测（例如描边特性、Web Worker），其余用 `isAcde()`。

### 2.2 运行时缺什么、怎么解决

| acde 的情况 | 影响 | 解决 |
|---|---|---|
| 没有 WebGL；WebGPU 只在 Linux 上有 | 没有 WebGPU 的平台看不到 3D | 不回退到 WebGL，显示平台提示，其余界面照常可用 |
| WebGPU 可能以兼容模式运行 | 部分后处理通道不可用 | 兼容模式下跳过 GTAO 和深度采集通道；acde 默认低画质档 |
| 没有 Web Worker | 几何脚本、Manifold 打印编译、KTX2/Draco 解码都依赖 Worker | 几何脚本和 Manifold 改在页面线程运行；纹理和模型在构建时预先转换（见 2.3） |
| OffscreenCanvas、`createImageBitmap` 不保证可用 | 截图流程和部分加载器 | 不可用时回退到普通 canvas 和图片元素 |
| 没有 `crypto.subtle` | 几何脚本产物的哈希 | 纯 JS 的 SHA-256 |
| 没有 Pointer Lock、Fullscreen API | 漫游模式转视角、全屏 | 按住拖拽转视角；全屏改用 acde 的窗口状态 |
| 不能从 CDN 加载 ES 模块、不能访问图标 API | Manifold、图标、材质、模型 | 全部在构建时放进应用自带的资源目录 |
| 没有 WebXR | VR 插件 | acde 下不注册、不启动 |
| 后端不开 TCP 端口，环境变量从零构建 | 数据目录、鉴权、来源校验 | 启动时按 acde 提供的变量补默认值：数据放进应用私有目录，鉴权走代理模式，放行 acde 页面的来源 |
| 不支持 SVG 的 `vector-effect: non-scaling-stroke` | 2D 平面图的细线被放大几十倍，糊成色块 | 在不支持的环境里把线宽换算成随缩放变化的值 |
| 应用不能改自己的窗口大小 | 侧边栏只能挤压或遮挡主界面 | 侧边栏停靠在右侧，可收起 |
| 界面语言只认网址参数 | 应用总是英文 | acde 下默认跟随会话语言 |

### 2.3 构建时的资源准备

`acde:prepare` 在 acde 调用 `next build` 之前运行，每一步都可重复执行：

| 步骤 | 做什么 |
|---|---|
| manifold | 把打印编译用的 Manifold 模块和 wasm 复制进应用资源 |
| assets | 镜像目录资源：KTX2 纹理转成 WebP，Draco 压缩的模型解压 |
| icons | 扫描源码里用到的图标，从本地图标包打成子集 |
| agent-host | 把 AI 团队的场景主机打成单独一个文件 |

### 2.4 值得记住的坑

这些问题都花了时间才定位，原因不在报错信息里。

**场景状态库不能进 Next 的服务端包。** 核心包的场景状态库带 `'use client'` 标记，路由的服务端包里它会被换成一个没有状态的客户端引用，表现为 `this.store.getState is not a function`，而在 bun 里直接跑的单测完全正常。所以进程内的 MCP server 在 `acde:prepare` 时单独打成一个文件，由后端在运行时原生加载，并通过构建配置确保它被带进安装包。应用代码只引用它的类型。

**3D 画布改变大小时整块变白约一秒。** 后处理管线把画布宽高列为重建条件，每次尺寸变化都销毁重建并重新编译着色器，而管线内部只用尺寸判断是否为 0。改成只在「有尺寸 ↔ 无尺寸」切换时重建。目前只在 acde 默认的低画质档下验证过。

**2D 平面图糊成色块。** 见 2.2 的描边一行。引擎能正确报告每个元素的缩放倍数，也支持 `calc(<像素值> * var(...))` 形式的线宽（注意必须带 `px` 单位，不带单位的乘法不生效）。

**文字间歇性重叠。** 栅格布局里写裸的 `fr` 列时，引擎会按内容的最窄宽度测量一遍，之后偶尔用那一遍的断行结果来绘制，盒子高度却按正常宽度算。把列写成最小值为 0 的形式可以避免。这个问题是间歇性的。

**构建卡死在 “Creating an optimized production build”。** Turbopack 会从 PATH 里起一个 `node` 跑 PostCSS。如果 PATH 里先找到的是很旧的系统 Node，构建会一直空等，没有任何报错。要保证满足仓库要求的 Node 版本排在 PATH 最前面。

**测试会话里的数据目录不在 HOME 下。** `acde test` 的每个会话把数据目录放在会话 HOME 的旁边，而不是里面；需要从会话外访问项目库的测试要按这个布局找。

**机器忙时端到端测试会超时。** 加载带 3D 模型的示例场景那一步有 5 秒的等待窗口，机器被占用时会超时。判断是否为回归前先看负载。

**翻译草稿不显示。** 仓库规则是 AI 起草的译文在人工审核前一律显示英文。新加的界面文案要人工确认后把词条标为已审核才会生效。

### 2.5 尚未验证或未完成

- 中、高画质档下，画布改变大小后不重建管线是否完全正常。
- 2D 平面图里鼠标悬停的高亮效果（无头测试里触发不了悬停）。
- 面板文字重叠的修复只按出问题的条件抽查过，间歇性问题无法证明已根除。
- 应用其余界面的中文：大量词条仍是未审核的草稿，显示为英文。
- 外部请求走代理的情况：后端只继承会话里的代理变量。

## 三、自进化设计（未实现）

> 本节是设计说明。仓库里**没有**任何自进化的代码，下面出现的文件名和数据结构都是提议。

### 3.1 目标

让 AI 团队从自己做过的活里学习，做两件事：

- **改进技能**：每个员工积累「下次怎么做更好」的经验，例如「放床之前先查素材库里床的实际尺寸」。
- **调整分工**：谁拿哪些工具、总管怎么拆任务、要不要增减岗位，随实际表现调整。

不做的事：不微调模型，不让 AI 改程序代码，不改场景工具本身的规则。进化的对象只是**数据**——提示词里的经验条目和团队配置。

### 3.2 能进化的是什么

现在这些内容是写死在 `employees.ts` 里的常量，自进化就是让它们变成「出厂设置 + 可覆盖的团队档案」：

| 层 | 现在在哪 | 进化后 |
|---|---|---|
| 员工的经验 | `EMPLOYEE_PROMPTS` 里的几条规则 | 出厂规则不动，后面追加学到的经验条目 |
| 员工的工具 | `EMPLOYEE_TOOLS` | 可增减，但只能从 MCP server 实际提供的工具里选 |
| 总管的拆任务规则 | `BOSS_PROMPT` | 追加调度经验，例如「改了布局必须先校核再布置家具」 |
| 岗位设置 | 固定四个员工 | 可提议拆分或新增岗位 |
| 运行参数 | 步数上限、返工轮数 | 可按岗位调整 |

出厂设置永远保留在代码里，团队档案随时可以清空回到出厂状态。

### 3.3 从哪里学

系统已经在产生这些信号，只是现在用完就丢：

| 信号 | 说明什么 |
|---|---|
| 工具拒绝及其错误码 | 员工哪里用错了工具；同一个码反复出现就是缺一条经验 |
| 校核员工的发现和返工 | 哪个岗位的活经常不合格、错在哪 |
| 人点了验收还是撤回 | 整件事做得对不对，最直接的评价 |
| 验收后人又手动改了什么 | AI 没做到位的地方 |
| 每个任务用了多少步、多少次模型调用 | 效率；步数顶到上限说明任务拆得太大或工具不够 |
| 员工遇到「工具清单里没有」的情况 | 分工不合适 |
| 人中途点了停止 | 方向错了或太慢 |

### 3.4 进化循环

```text
记录 ──▶ 复盘 ──▶ 提议 ──▶ 评测 ──▶ 采纳 ──▶（下一次任务用上）
                              │         │
                              └─ 不达标 ─┴─▶ 丢弃，或回滚
```

**记录。** 每次任务结束写一份工作日志：这句话、任务列表、每个员工的每次工具调用及结果、校核发现、最终是验收还是撤回、步数。日志存在应用私有数据目录里，只在本机。

**复盘。** 任务结束后（不占用任务本身的时间），由一个「复盘」角色读日志，回答三个问题：哪里出了错或绕了路？是偶然还是会再发生？如果会，是缺经验、缺工具，还是任务拆得不对？

**提议。** 复盘的产出不是直接改配置，而是结构化的提议，每条都带依据：

| 提议类型 | 例子 |
|---|---|
| 给某员工加一条经验 | 室内员工：「放家具前用 search_assets 确认素材的实际尺寸，不要假设标准尺寸」 |
| 改写或删除一条经验 | 两条经验说的是同一件事，合并 |
| 给某员工增减工具 | 平面员工三次需要 `measure` 以外的测量手段 |
| 调整总管的拆任务规则 | 家具任务应排在校核布局之后 |
| 新增或拆分岗位 | 室内员工的任务总是顶到步数上限，拆成「家具」和「饰面」 |
| 调参数 | 校核员工的步数上限偏高 |

**评测。** 提议生效前先证明它没让事情变差：用一组固定的基准任务（例如「加一间卧室」「两居改三居」「布置一间双床房」），在临时场景上用带提议和不带提议的配置各跑一遍，比较 3.6 的指标。

**采纳。** 早期所有提议都要人确认（面板里列出提议、依据和评测结果，人点同意或拒绝）。采纳后团队档案生成一个新版本。之后几次真实任务的指标如果明显变差，自动回滚到上一版并记录原因。

### 3.5 护栏

自进化最大的风险是越改越偏，所以先定死这些：

- **只读岗位永远只读。** 校核和出图员工不能获得会改场景的工具，任何提议都不行。
- **员工不能给自己放权。** 提议由复盘角色提出、由人或评测批准，执行任务的员工不参与自己的配置。
- **工具只能从现有清单里选。** 不能提议不存在的工具，也不能绕过工具直接改数据。
- **提示词有预算。** 每个岗位的经验加工具说明有总字数上限；超了必须先合并或淘汰旧经验，不能无限追加。
- **经验必须是通用的。** 不能写进某个具体项目的坐标、房间名、节点 id。
- **每次变更可追溯、可回滚。** 每个版本记录改了什么、依据哪几次任务、评测结果、谁批准的。
- **一次只改一处。** 多个提议不同时生效，否则分不清是哪条起了作用。
- **日志不出本机。** 工作日志里有用户的原话和场景内容。

### 3.6 用什么衡量

| 指标 | 含义 |
|---|---|
| 验收率 | 做完后人点验收的比例 |
| 撤回率 | 人点撤回的比例 |
| 返工率 | 校核打回的比例 |
| 每个任务的工具拒绝次数 | 用错工具的频率 |
| 每个任务的步数和模型调用次数 | 效率和成本 |
| 验收后人工修改量 | AI 没做到位的程度 |

验收率和撤回率最重要，其余用来解释它们为什么变化。

### 3.7 落在现有代码的哪里

实现时预计动这几处，都是数据通路上的改动，不涉及场景工具：

| 位置 | 改什么 |
|---|---|
| `scene-agent.ts` | 任务过程中把事件写进工作日志；组装员工提示词时读团队档案（出厂规则 + 经验）；工具清单从团队档案取 |
| `employees.ts` | 现有常量改名为出厂设置，结构不变 |
| `session.ts` | 任务结束时触发复盘（异步，不阻塞验收） |
| 新增：团队档案和工作日志的读写 | 存放方式沿用 `settings.ts`：应用私有数据目录下的文件 |
| 新增：复盘和评测 | 复盘是一次模型调用加结构化输出；评测复用现有的进程内场景主机，在临时场景上跑 |
| `agent-panel.tsx` | 增加「团队成长」视图：当前经验、待批准的提议、版本历史 |

### 3.8 和上游规则的关系

仓库的架构约定里有两条和这里直接相关：

- **规则应该在工具里，不在循环里。** 如果某条「经验」其实是所有 agent 都该遵守的硬规则（例如某种放置必然碰撞），正确的归宿是进场景工具的校验，让工具直接拒绝，而不是只留在本地团队的提示词里。
- **知识要对齐。** 一条改变「agent 应该怎么建」的经验，如果普遍成立，应该经人审核后进到公开的 agent 指南和技能里，让外部 agent 也受益。

所以本地学到的经验分两类：只和本团队分工有关的留在团队档案里；普遍成立的，复盘时标记为「建议上游」，由人决定是否提交到工具或指南。自进化不自动改上游内容。

### 3.9 分阶段

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | 只记录工作日志和指标 | 有数据可看，不改变任何行为 |
| 1 | 复盘产出提议，只展示不生效 | 验证提议的质量 |
| 2 | 经验类提议经人批准后生效，带版本和回滚 | 技能开始改进 |
| 3 | 工具分配和总管规则可调整 | 分工开始调整 |
| 4 | 基准任务评测；低风险提议可自动采纳 | 减少人工批准 |
| 5 | 新增和拆分岗位 | 团队结构可变 |

每一阶段都以前一阶段的数据为依据，不建议跳过阶段 0 和 1。

### 3.10 还没想清楚的问题

- 基准任务从哪来、多少个才够：太少会过拟合，太多评测一次的成本就高。
- 评测要调用真实模型，每次提议的成本需要估算。
- 换了模型之后，旧模型积累的经验是否还适用，要不要按模型分开存。
- 多个用户或多台机器之间要不要共享团队档案。
- 人长期只点「同意」时，批准这一关就失去了作用，需要有别的检查。
